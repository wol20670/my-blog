# 게시글 메타데이터 점검

`_posts/`의 글 하나를 대상으로 "게시 직전 점검"만 한다. 본문 문체, 제목 문구, heading 구조, categories 분류 체계는 절대 건드리지 않는다. 전역 작성 규칙은 `CLAUDE.md`를 참고하되 여기 다시 옮겨 적지 않는다.

## 1. 대상 파일 정하기

사용자가 파일을 안 짚어줬다고 바로 물어보지 마라. 먼저 판단해라.

- 방금 대화에서 다루던 글, 방금 IDE에서 연 파일이 있으면 그걸 쓴다.
- `git status --short -- _posts/`로 변경된 파일이 정확히 하나면 그걸 쓴다.
- 그래도 후보가 여러 개거나 애매하면 그때만 물어봐라.

## 2. Front Matter 검사
아뇨 추천고 `_config.yml` 기본값이 채워준다. 이런 필드는 없다고 지적하지 않는다).
- `title`: 콜론 등 특수문자 있으면 따옴표로 감싸도록 정리. 문구 자체는 바꾸지 않는다.
- `date`: `YYYY-MM-DD HH:MM:SS +0900` 형식과 `+0900` 확인. 미래 날짜면 경고만 하고 임의로 안 바꾼다.
- `description`: 있으면 형식만 정리(보존). 없다고 새로 지어내지 않는다.
- `categories`: 존재/형식만 확인. 비어 있거나 이상해도 경고만 하고 새로 만들거나 바꾸지 않는다. "categories는 항상 몇 개"류의 규칙을 만들지 않는다. 다만 허용값은 `Troubleshooting` 또는 `Exploration` 단일값으로 정해져 있으므로(`CLAUDE.md` 8.2절), 그 외의 값(예: `[Git, GitHub]`, 복수 값, 다른 문자열, 대소문자가 다른 표기)이면 "현재 taxonomy와 맞지 않음"으로 경고만 하고 실제 값은 바꾸지 않는다. 본문을 보고 어느 쪽이 맞는지 자동으로 골라서 고치지 않는다.
- `mermaid`: 본문에 ` ```mermaid ` 블록이 있는데 `mermaid: true`가 없으면 추가한다(렌더링 안 되는 실제 버그). 블록도 없는데 플래그만 있어도 굳이 지우지 않는다.

## 3. 파일명 / 날짜 검사

- 파일명이 `YYYY-MM-DD-slug.md` 형식인지 확인.
- **신규/기존 판별**: `git ls-files --error-unmatch <경로>` 기본 사용 (성공하면 기존 글). 단 이것만 절대 기준으로 삼지 마라 — 기존 글을 stage 안 하고 방금 rename했다면 새 경로가 untracked로 보일 수 있다. `git status --short -- _posts/`에서 옛 경로 삭제(`D`)와 새 경로 등장(`??`/`A`)이 같이 보이면 rename으로 보고 신규 글로 단정하지 않는다.
- 파일명 날짜와 Front Matter `date`가 이미 같으면 그냥 둔다.
- 다르면: 신규 글이면 의도한 날짜를 물어보고 맞춘다. 기존 글이면 Front Matter `date`는 그대로 두고(발행일 보존), 파일명 쪽을 맞출지 사용자에게 확인한다. **"수정했다"는 이유로 기존 글 날짜를 오늘 날짜로 바꾸지 마라.**
- **slug 충돌**: 같은 `_posts/` 안에 날짜만 다르고 slug가 같은 파일이 있으면 보고한다. 먼저 발행된 글의 URL(=slug) 유지를 기본으로 제안하되, 실제 rename은 항상 사용자 확인 후에만 한다. rename할 파일이 tracked면 `git mv`, untracked면 일반 rename 후 `git add`. 날짜 부분은 안 건드리고 slug만 바꾼다. 충돌 없는 정상 slug를 예쁘게 다듬으려고 rename하지 않는다.

## 4. tags 검사/추천

- 먼저 `_posts/` 전체 글의 Front Matter `tags`만 훑어서 현재 쓰이는 표기(소문자, 하이픈 등)를 파악한다. 본문까지 매번 다 읽을 필요는 없다.
- 대상 글에 실제로 붙일/뺄 tag는 반드시 **대상 글 본문 내용**만 근거로 판단한다. 본문에 없는 걸 추측해서 넣지 않는다.
- 다음은 **바로 고쳐도 되는 것** (결정론적): 대소문자 정규화, 완전 중복 제거, 기존 vocabulary와 같은 뜻인데 표기만 다른 걸 통일, YAML 형식 오류.
- 다음은 **추천만 하고 사용자 확인 후 적용**: 새 tag 추가, 기존 tag 삭제.
  - 단, 사용자가 "태그 정리해줘", "적절한 태그 넣어줘"처럼 실제 변경까지 명시적으로 요청했으면 그 요청을 승인으로 보고 본문 근거 안에서 바로 적용해도 된다.
- 이미 붙은 tags가 본문과 맞으면 그대로 둔다. 너무 일반적인 단어나 의미 겹치는 중복은 정리 대상으로 짚어준다.
- categories는 이 단계에서 다루지 않는다.

## 5. 마무리

확인/수정한 항목과, 바꾸지 않고 넘어간 항목·이유를 요약해서 보고한다. 이미 다 맞는 글이면 "수정할 것 없음"으로 끝낸다(같은 글에 다시 실행해도 불필요한 변경이 없어야 한다).

## 하지 않는 것

본문 재작성, 문체 개선, 제목 자동 개선, heading 재구성, 문단 순서 변경, categories 자동 추천/분류 체계 변경, 충돌 없는 slug를 이유 없이 바꾸기, 여러 스크립트/파이프라인 구성.
