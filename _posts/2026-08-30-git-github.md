# Git Conflict를 줄이기 위해 줄 번호를 나누면 될까?

## 문제 상황

팀원 여러 명이 같은 파일을 수정하고 Merge Conflict를 유도하고 횟수를 줄이는 과정에서 문제가 발생했다.

처음에는 단순히 기존에 존재하던 소스들을 냅두고 그 아래 각자 다른 줄번호에 내용을 추가하면 충돌을 피할 수 있을 것이라고 생각했다. 하지만 각자가 다른 줄번호의 내용을 수정하더라도 충돌이 발생했다.

예를 들어 하나의 파일을 다음처럼 담당한다고 생각했다.

```text
ccode 1~5
```
위와 같은 상태의 브런치를 모두 git pull하여 각자 새로운 브런치를 만들고 시작한다.

```text
code 1~5
6번 줄   → A
7번 줄  → B
8번 줄 → C
9번 줄 → D
```

A가 6번 줄을 수정하고 B가 7번 줄을 수정한다면 서로 다른 줄을 수정하는 것이므로 충돌하지 않을 것이라고 예상했다.

---

## 처음 생각한 원인

처음에는 Git이 파일을 병합할 때 **현재 파일의 줄 번호를 기준으로 변경 사항을 비교한다**고 생각했다.

그래서 Conflict가 발생하는 원인도 다음과 같을 것이라고 생각했다.

```text
A와 B가 같은 줄 번호 수정
        ↓
Conflict 발생

A와 B가 다른 줄 번호 수정
        ↓
자동 병합
```

그렇다면 팀원마다 수정 가능한 줄 번호를 미리 정해놓으면 Conflict를 줄일 수 있을 것 같았다.

---

## 시도한 방법

팀원들이 하나의 파일을 수정하되 서로 수정하는 위치가 겹치지 않도록 작업 영역을 나눠보았다.

처음에는 이를 단순하게 **줄 번호 단위**로 생각했다.

```text
A 담당 → 파일 상단
B 담당 → 그 아래
C 담당 → 그 아래
D 담당 → 파일 하단
```

또 수정 위치 사이에 빈 줄을 많이 넣으면 변경된 코드가 서로 멀어지기 때문에 충돌 가능성이 더 줄어드는 것은 아닐까 생각했다.

예를 들면 다음과 같은 구조다.

```text
A 내용




B 내용




C 내용
```

또는 각자 정확히 5줄씩 담당하도록 하면 Git이 변경 사항을 더 쉽게 구분하지 않을까 생각했다.

---

## 결과

실험하면서 알게 된 것은 **줄 번호 자체는 핵심이 아니라는 것**이었다.

예를 들어 공통 원본이 다음과 같다고 하자.

```javascript
function A() {
  hello();
}

function B() {
  bye();
}
```

학생1이 `A()`에 코드를 한 줄 추가한다.

```javascript
function A() {
  hello();
  meet();
}

function B()) {
  bye();
}
```

그러면 기존 `B()`의 줄 번호는 한 줄씩 아래로 밀린다.

하지만 다른 브랜치에서 학생2가 `B()`을 수정했다고 해서 단순히 **줄 번호가 변경됐다는 이유만으로 Conflict가 발생하는 것은 아니었다.**

즉,

```text
줄 번호가 변경됨
≠
Merge Conflict 발생
```

이었다.

또한 A()와 B() 사이에 빈 줄을 여러 개 넣는 것도 Conflict를 방지하는 확실한 방법은 아니었다.

빈 줄 역시 Git 입장에서는 하나의 텍스트 라인일 뿐이기 때문이다.

---

## 실제 원인

중요한 것은 단순한 줄 번호가 아니라 ***원본을 기준으로 두 브랜치의 변경 영역이 어떻게 겹치는가***였다.

예를 들어 공통 원본에 다음 두 영역이 있다고 하자.

```text
[A 영역]
기존 내용

[B 영역]
기존 내용
```

A가 자신의 영역만 수정한다.

```text
[A 영역]
A가 수정한 내용

[B 영역]
기존 내용
```

B 역시 다른 영역만 수정한다.

```text
[A 영역]
기존 내용

[B 영역]
B가 수정한 내용
```

그러면 Git은 두 변경 사항을 비교해서 다음과 같이 합칠 수 있다.

```text
[A 영역]
A가 수정한 내용

[B 영역]
B가 수정한 내용
```

반대로 A와 B가 공통 원본의 같은 부분을 서로 다르게 변경한다면 상황이 달라진다.

A:

```text
[A 영역]
A가 수정한 내용
```

B:

```text
[A 영역]
B가 수정한 내용
```

이 경우 Git은 두 변경 사항 중 ***어느 것이 최종 결과가 되어야 하는지 스스로 판단할 수 없다.***

따라서 Merge Conflict가 발생할 수 있다.

Git은 단순히 현재 파일의 절대적인 줄 번호를 보는 것이 아니라, **두 브랜치의 공통 조상(common ancestor)을 기준으로 변경된 내용과 그 주변 문맥을 비교하여 병합**한다.

따라서 핵심은

```text
A가 몇 번째 줄을 수정했는가
```

가 아니라

```text
A와 B의 변경 영역이 서로 충돌하는가
```

에 가깝다.

> 같은 줄을 수정해야만 Conflict가 발생하는 것도 아니다. 서로 인접한 변경이 하나의 변경 영역으로 판단되거나, 한쪽이 다른 쪽이 수정한 주변 구조를 크게 변경한 경우에도 Conflict가 발생할 수 있다.

---

## 해결 방법

그래서 줄 번호를 나누는 방식 대신 **수정해야 하는 논리적인 영역 자체를 분리하는 방식**으로 생각을 바꿨다.

예를 들어:

```text
[A 담당 영역]
A가 수정할 내용

[B 담당 영역]
B가 수정할 내용

[C 담당 영역]
C가 수정할 내용

[D 담당 영역]
D가 수정할 내용
```

처럼 각 팀원이 자신의 영역을 담당하도록 했다.

핵심은 다음과 같았다.

```text
A → 1~5번 줄
B → 6~10번 줄
```

이 아니라

```text
A의 변경 범위와 B의 변경 범위가
가능한 한 서로 겹치지 않도록 만든다.
```

는 것이다.

따라서 5줄씩 담당하게 해서 Conflict가 줄어드는 것이 아니라, **그 5줄이 각각 독립적인 작업 영역이었기 때문에 Conflict 가능성이 줄어드는 것**이었다.

---

## 더 나은 방법

이 원리를 실제 개발에 적용하면 줄 번호보다는 **기능과 책임 단위로 작업을 분리하는 것**이 더 적절할 것이다.

예를 들어 다음과 같은 방식이다.

```text
A → 로그인 기능
B → 회원가입 기능
C → 프로필 컴포넌트
D → 결제 서비스
```

코드는 계속 추가되고 삭제되기 때문에 다음과 같은 구분은 유지하기 어렵다.

```text
A → 1~30번 줄
B → 31~60번 줄
```

반면 다음과 같은 단위는 줄 번호보다 의미가 명확하다.

```text
login()
signup()
UserProfile
PaymentService
```

따라서 Conflict를 줄이기 위해서는 단순히 파일 안에서 위치를 떨어뜨리는 것보다 다음과 같은 방식이 더 효과적이다.
>충돌을 줄이는 세부적인 방안으로 GPT에게 조언을 받아서 작성했습니다.

- 같은 함수나 컴포넌트를 여러 사람이 동시에 수정하지 않도록 작업을 조율한다.
- 큰 기능을 서로 독립적인 작은 작업 단위로 분리한다.
- 한 파일이나 한 모듈에 너무 많은 책임이 몰리지 않도록 구조를 나눈다.
- 변경 범위를 가능한 한 작게 유지한다.
- 작업 브랜치를 너무 오래 유지하지 않고 기준 브랜치의 변경 사항을 자주 반영한다.

특히 마지막 부분도 중요하다.

작업 영역을 아무리 잘 나눠도 한 브랜치를 오래 유지하면 그동안 `main`에 많은 변경이 쌓이면서 병합해야 할 차이가 커진다.

따라서 **작업 영역 분리 + 작은 변경 단위 + 자주 통합하기**를 같이 사용하는 것이 더 현실적인 방법이다.

---

## 배운 점

처음에는 Git Conflict가 줄 번호를 기준으로 발생한다고 생각했다.

그래서 팀원마다 수정할 줄 번호를 정해놓으면 충돌을 줄일 수 있을 것이라고 예상했다.

하지만 실제로 중요한 것은 **몇 번째 줄을 수정했는지가 아니라 공통 원본을 기준으로 각 브랜치의 변경 영역이 서로 겹치는가**였다.

코드가 추가되거나 삭제되면 줄 번호는 쉽게 변한다. 따라서 협업할 때는 줄 번호보다 함수, 컴포넌트, 기능, 파일과 같은 **논리적인 책임 단위로 작업 영역을 분리하는 것이 더 효과적**이다.
